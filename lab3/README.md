# Лабораторна робота № 3. Реалізація власного blockchain

Дисципліна: Інформаційна безпека та децентралізовані технології (ХНУРЕ).

Проєкт UniCoin: мінімальна облікова система на основі блокчейну для внутрішніх бонусних токенів університету.

## Terms of reference (коротке технічне завдання)

### 1. Огляд та призначення системи

UniCoin призначений для обліку бонусних токенів, які студенти отримують за участь у житті університету (олімпіади, волонтерство, наукові конференції, спортивні змагання) та витрачають у підрозділах університету (їдальня, бібліотека, друк, сувенірна крамниця). Сьогодні подібні бонуси ведуться у таблицях окремих підрозділів, тому студент не може перевірити правильність нарахувань, а записи можна змінити заднім числом. Блокчейн забезпечує незмінність і прозорість історії: кожен учасник може самостійно перевірити, що його баланс відповідає підтвердженим операціям.

Кейс належить до груп "Цифрові активи та валюти" та "Системи обміну даними" з переліку методичних вказівок.

### 2. Зміст системи (межі системи)

До системи входять:

* бібліотека `minichain` (класи Hash, KeyPair, Signature, Account, Operation, Transaction, Block, Blockchain);
* кран (faucet) для початкового нарахування токенів адміністрацією;
* засоби валідації блоків і повного аудиту історії (`verifyChain`);
* демонстраційний сценарій `demo.py` та набір автотестів.

Поза межами системи (в поточній версії): мережевий рівень (P2P), механізм консенсусу між кількома валідаторами, постійне сховище, графічний інтерфейс, обмін токенів на гроші.

### 3. Взаємодія з іншими продуктами та компонентами

* Інформаційна система університету (деканат, студентський відділ): ініціює нарахування токенів через кран.
* POS-термінали їдальні, бібліотеки: приймають платежі, тобто формують операції на рахунок підрозділу.
* Мобільний гаманець студента: генерує ключі, підписує операції, показує баланс.
* Аудитор (студентська рада, контрольний відділ): незалежно перевіряє історію блоків.

Взаємодія відбувається через програмний інтерфейс бібліотеки; у промисловій версії передбачається REST API вузла.

### 4. Функції продукту

1. Генерація ключових пар ECDSA secp256k1 та створення облікових записів (accountID = SHA-1 від відкритого ключа).
2. Підтримка кількох ключів в одному гаманці.
3. Нарахування тестових токенів через кран з лімітом на один запит.
4. Створення та підпис операцій платежу; об'єднання операцій у транзакції.
5. Формування блоків з коренем дерева Меркла та спрощеним Proof-of-Work.
6. Валідація блоку перед додаванням до історії (посилання на останній блок, унікальність транзакцій і операцій, конфлікти, підписи, баланси).
7. Ведення бази балансів (coinDatabase), бази транзакцій (txDatabase) та використаних операцій (opDatabase).
8. Повний аудит історії з виявленням будь-якої зміни даних.

### 5. Вимоги до безпеки

* Підробка платежу неможлива без особистого ключа відправника: кожна операція підписується ECDSA (SHA-256, RFC 6979, low-s).
* Особистий ключ недоступний ззовні класу KeyPair.
* Ключ підпису перевіряється за реєстром облікових записів блокчейну, а не за об'єктом, наданим клієнтом.
* Захист від подвійної витрати та перевитрати: баланс перевіряється з урахуванням усіх попередніх операцій блоку.
* Захист від повтору: кожна операція має унікальний nonce, використані операції зберігаються в opDatabase; транзакції мають унікальний nonce і перевіряються за txDatabase.
* Цілісність історії: блоки пов'язані через prevHash (SHA-256), транзакції захищені коренем Меркла; зміна будь-якого блоку виявляється функцією verifyChain.
* Обмеження емісії: загальний обсяг крана та ліміт на один запит.

### 6. Характеристики користувачів

* Студент: власник гаманця, отримує і витрачає токени, технічна підготовка базова.
* Підрозділ університету (їдальня, бібліотека): приймає платежі, переглядає баланс.
* Адміністратор: керує краном і реєстрацією учасників.
* Валідатор (сервер університету): формує та перевіряє блоки.
* Аудитор: перевіряє коректність історії.

### 7. Обмеження

* Один валідатор, консенсус не реалізовано (permissioned, приватний блокчейн).
* Дані зберігаються в оперативній пам'яті.
* Нарахування з крана змінює coinDatabase напряму і не записується в блоки (як передбачено методичними вказівками); у промисловій версії це має бути окрема підписана емісійна транзакція.
* Арифметика еліптичної кривої реалізована на чистому Python і не захищена від атак по часу виконання; для промислового використання потрібна перевірена бібліотека.
* Python 3.10+, без сторонніх залежностей (pytest і cryptography потрібні лише для тестів).

## Архітектура

| Клас | Файл | Призначення |
|---|---|---|
| Hash | `minichain/hash.py` | toSHA1 (accountID), toSHA256 (ID транзакцій і блоків) |
| KeyPair, Signature | `minichain/signature.py` | ECDSA secp256k1, власна реалізація арифметики кривої |
| Account | `minichain/account.py` | гаманець, баланс, створення та підпис операцій |
| Operation, Transaction | `minichain/operation.py` | платіж і набір платежів з nonce |
| Block | `minichain/block.py` | блок з prevHash, коренем Меркла та PoW |
| Blockchain | `minichain/blockchain.py` | історія, бази даних, кран, валідація, аудит |

## Запуск

```bash
python demo.py               # сценарій роботи та спроби атак
pip install pytest cryptography
python -m pytest -v          # 18 автотестів
```
